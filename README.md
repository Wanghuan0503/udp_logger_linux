# udp_logger

Thor 控制器上的 **MCU 数据 UDP 接收与日志记录** 程序。

当前版本是**框架骨架**：整条数据流水线已经打通并可运行，
**协议解析是空实现占位**（收到任何报文都原样留档，不做解析）。
等 MCU 协议确定后，只需要修改 `src/parser.cpp` 一个文件。

---

## 1. 它做什么

```
MCU ──UDP──▶ [线程1 udp-recv] ──▶ 有界队列 ──▶ [线程2 udp-parse] ──▶ 日志文件
              recvfrom 收包        削峰填谷       解析 + 写日志
```

- **线程1 `udp-recv`**：只做 `recvfrom` 和入队。不解析、不写磁盘，路径尽可能短，避免丢包。
- **线程2 `udp-parse`**：出队 → 解析 → 写日志。写磁盘慢也不影响收包。
- **队列有界**：过载时表现为"可控丢包并计数"，而不是把内存吃爆。
- **两级日志**：结构化日志（glog，按级别分文件）+ 原始报文 hex 留档（独立文件）。

./build/udp_sender

## 5. 查看日志

日志**一启动就开始写**（不需要先收到 MCU 数据）—— 启动横幅、生效配置、监听就绪
这些信息在程序起来的那一刻就已经落盘了。

```bash
# 方式一（推荐，最省心）：直接看目录里最新的 INFO 文件
tail -f "$(ls -t logs/udp_logger.INFO.* | head -1)"

# 方式二：软链接始终指向最新的 INFO 文件
tail -f logs/udp_logger.INFO

# 看有没有丢包和解析问题
grep -E "丢弃|解析失败" "$(ls -t logs/udp_logger.WARNING.* | head -1)"

# 看原始报文留档（协议未定期的主要依据）
tail -f logs/raw/udp_raw.log
```

> 程序启动时会打印一行 `实时查看（软链接，始终指向最新文件）: tail -f ...`，
> 直接复制那行命令即可，不用记文件名规则。
>
> **文件名规则**：`<前缀>.<级别>.<主机名>.<用户名>.log.<日期>-<时间>.<pid>`。
> 每次重启都会生成一个新文件，这是正常的（glog 的设计：按进程实例分文件）。

日志内容示例（当前占位解析器下）：

```
I1012 16:40:12.345678 12345 app.cpp:210] [原始报文] src=127.0.0.1:54321 recv_time=2025-10-12 16:40:12.345 len=32 hex=00 00 00 00 3F 8A ...
I1012 16:40:12.345679 12345 app.cpp:225] [接收统计] 累计收到=10 累计丢弃=0 零长包=0 recv错误=0 队列深度=0/4096 峰值深度=3
I1012 16:40:17.345679 12345 app.cpp:230] [接收统计·空闲] (距上一个包 5000ms) 累计收到=10 累计丢弃=0 ...
I1012 16:40:22.345679 12345 app.cpp:310] [处理统计·空闲] 累计处理=10 解析失败=0 队列深度=0/4096 峰值深度=3 (距上一个包 10000ms)
```

**每 5 秒打印一次统计**，有数据时是 `[接收统计]`，没数据时是 `[接收统计·空闲]`。
这样**即使 MCU 完全不发数据，日志里也有记录** —— 现场能立刻区分
"MCU 没发"和"程序没收"。从未收到过数据时还会额外提示该检查什么。

关键字段：

| 字段 | 含义 |
|---|---|
| `累计收到` | 应用从内核读出的报文总数 |
| `累计丢弃` | 因队列满被丢弃的数量（应用层丢包） |
| `recv错误` | `recvfrom` 返回致命错误的次数 |
| `队列深度=X/Y` | 当前积压 / 容量 |
| **`峰值深度`** | **历史最深积压。长期贴着容量上限 = 消费能力不足** |
| `距上一个包` | 数据是否真的停了 |

> **丢包评价的注意事项**：**测试时长必须明显大于 5 秒统计间隔**。
> 5 秒的压测最多只能跨过一个统计周期，甚至看不到统计；而且短测试只测到
> 最恶劣的初始饱和阶段，丢包率会被显著放大（实测：同样条件下 5 秒测出 29%，
> 25 秒测出 17%）。评价稳态性能请跑 **30 秒以上**。

## 6. 配置

只有一个配置文件：`config/config.yaml`，每个字段都有注释。
改完重启程序生效（本期不支持热加载）。

最常改的两个字段：

```yaml
network:
  bind_ip: "0.0.0.0"    # 监听所有网卡；也可写具体网卡 IP
  bind_port: 9000       # 监听端口，请用 1024 以上
```

配置写错时程序会给出明确的中文报错并退出，例如：

```
配置加载失败:
network.bind_port 必须大于 0（建议 1024~65535，低于 1024 需要 root 权限）
```

程序启动时还会把**全部生效配置**打进日志，方便核对"改的文件是不是生效的那个"。

## 7. 协议确定后要改哪里

**只改 `src/parser.cpp`**，具体步骤已经写在该文件的头部注释里，那里还准备好了
`u16()/u32()/u16be()/u32be()/crc16_ccitt()` 等工具函数，可直接使用。

可能还需要按真实字段调整 `include/packet.h` 里的 `ParsedMessage`。

其余模块（接收、队列、日志、配置）**一行都不用动**，这是本框架的主要设计目标。

## 9. 当前阶段的已知限制

| 限制 | 说明 |
|---|---|
| 解析未实现 | 协议未定，属预期。所有报文走 `[原始报文]` 记录分支 |
| 不支持热加载配置 | 改配置需重启。这是刻意的取舍（避免共享配置的加锁复杂度） |
| 不做下行通道 | 本期只收不发。若将来要回发 ACK，需要新增发送侧的队列与线程 |
| `queue.full_policy` 仅 `drop_new` 生效 | `drop_old` 配置项已校验但未实现对应行为 |
| 未做单元测试框架 | 目前靠 `udp_sender` + 手工验证。协议确定后建议补 gtest |
