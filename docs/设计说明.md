## 1. 数据流与线程模型

```
                    ┌──────────────────────────────────────┐
   MCU ──UDP包──▶   │  线程1: udp-recv                      │
                    │  ① recvfrom() 阻塞最多 200ms          │
                    │  ② 组包: 字节 + 来源IP:端口 + 接收时刻 │
                    │  ③ queue.TryPush()  ← 非阻塞，满了就丢  │
                    └───────────────┬──────────────────────┘
                                    │  LockFreeQueue<RawPacket>
                                    │  容量 = queue.capacity（有界）
                                    │  空则消费者睡眠，不占 CPU
                    ┌───────────────▼──────────────────────┐
                    │  线程2: udp-parse                     │
                    │  ④ queue.WaitPop(200ms) ← 有数据立刻醒 │
                    │  ⑤ 写原始报文 hex（独立文件+独立锁）    │
                    │  ⑥ parser.Parse()                    │
                    │  ⑦ LOG(INFO/WARNING) 按结果分支        │
                    │  ⑧ 每 5 秒汇报（空闲时也汇报）          │
                    └───────────────┬──────────────────────┘
                                    ▼
                 logs/udp_logger.INFO / .WARNING / logs/raw/udp_raw.log
```

| 线程 | 名字 | 允许做的事 | 绝对不做 |
|---|---|---|---|
| 主线程 | — | 读配置、初始化日志、注册信号、创建/join 线程、等待退出 | 不碰业务数据 |
| 线程1 | `udp-recv` | `recvfrom`、组包、入队、统计计数 | 不解析、不写磁盘、不做重活 |
| 线程2 | `udp-parse` | 出队、解析、写日志、统计计数 | 不做网络 IO |

**为什么必须分开**：`recvfrom` 手快有手慢无，内核 socket 缓冲区满了就直接丢包；
而写磁盘是毫秒级操作。单线程下"写日志的这段时间"足以丢掉一批包。
分开之后收包路径只有"拷贝内存 + 入队"两件事，微秒级完成。

**线程间共享的三个东西**（共享面越小，出并发 bug 的概率越低）：

| 共享对象 | 保护方式 | 说明 |
|---|---|---|
| `App::queue` | 队列内部 `mutex` + `condition_variable` | 唯一的数据通道 |
| `App::config` | 无锁，但**启动后只读** | 只读共享是安全的。改配置需重启 |
| `App::running` | `std::atomic<bool>` | 退出标志，多线程读写 + 信号处理函数写 |

## 2. 关机时序（顺序不可调换）

```
SIGINT/SIGTERM
   │
   │ 信号处理函数只做一件事： g_stop_requested.store(true)
   ▼
主线程轮询发现标志（每 200ms 检查一次）
   │
   ├─ ① app.running = false          通知接收线程；它最多在 recv_timeout_ms 后超时返回
   ├─ ② app.queue.Close()            立即唤醒可能正睡着的处理线程；并标记"不会再有新数据"
   ├─ ③ recv_thread.join()           接收线程收尾：关闭 socket，再调一次 Close()（幂等兜底）
   ├─ ④ proc_thread.join()           处理线程把队列里**剩余数据全部处理完**后才退出
   ├─ ⑤ ShutdownGoogleLogging()      刷盘，否则最后几行日志可能丢
   └─ ⑥ return 0
```

**三个容易写错的点**：

1. **第 ② 步不能省，也不能晚**。如果只设 `running=false` 而不 `Close()`，
   处理线程会永远睡在 `wait()` 上（它等的是"有数据或已关闭"，`running` 它看不见），
   于是 `join()` 永远不返回，`Ctrl+C` 失效。
2. **`Close()` 必须幂等**。接收线程退出时也会调一次做兜底，重复调用必须无害。
3. **不能在第 ④ 步之前刷盘**。`ShutdownGoogleLogging()` 之后就不能再写日志了，
   而处理线程退出时还要打一行"处理线程退出"统计。

**为什么信号处理函数里只能写 atomic**：信号可能在任意指令处打断主线程。
若那一刻主线程正持有 glog 内部锁，信号处理函数里再调 `LOG()` 去抢同一把锁
→ 立即死锁。`std::atomic<bool>` 的写入是 lock-free 的，不会与其他代码抢锁。

## 3. 文件职责一览

| 文件 | 职责 | 关键实现点 |
|---|---|---|
| `include/packet.h` | 数据对象定义 | `payload` 用 `vector<uint8_t>`；带上来源 IP 和接收时刻 |
| `include/lockfree_queue.h` | 有界线程安全队列 | 模板类；`TryPush` 非阻塞；`WaitPop` 返回三态（`kGotItem`/`kTimeout`/`kClosed`），内部用谓词形式的 `wait`/`wait_for` |
| `include/config.h` / `src/config.cpp` | YAML → 配置对象 + 校验 | 每字段有默认值；`if (node["k"])` 保护；校验失败给中文提示 |
| `include/logger.h` / `src/logger.cpp` | glog 初始化、原始日志、旧日志清理 | `alsologtostderr`（不是 `logtostderr`）；自带 `PruneOldLogs` |
| `include/parser.h` / `src/parser.cpp` | 协议解析 | **当前空占位**，返回 `kNotImplemented`；已备好读取工具函数 |
| `include/app.h` / `src/app.cpp` | socket 创建绑定 + 两个线程循环 | `SO_RCVTIMEO` 是退出关键；`LOG_EVERY_N` 降频 |
| `src/main.cpp` | 生命周期与关机时序 | 信号注册、队列重建、关机顺序 |
| `tools/udp_sender.cpp` | MCU 模拟器 | 可调目标/包数/速率/大小/固定 hex |

## 4. 关键参数取值理由

| 参数 | 默认值 | 为什么是这个值 |
|---|---|---|
| `recv_timeout_ms` | 200 | 权衡：太小则接收线程空转频繁；太大则 `Ctrl+C` 后要等很久才退出。200ms 内退出，人感觉是"立即" |
| `recv_buffer_bytes` | 65536 | 内核为每个 socket 预留的接收缓冲。注意内核实际值会被翻倍，程序启动时会用 `getsockopt` 复核并打进日志 |
| 接收缓冲区（用户态） | 65507 | IPv4 UDP 单包理论上限。用满值保证任何包都不会被 `recvfrom` 截断 |
| `queue.capacity` | 4096 | 按单包 1KB 估算约 4MB 内存，对控制器可接受；同时足够吸收秒级突发 |
| `max_size_mb` | 100 | 控制器磁盘通常有限，100MB 便于人工查看和归档 |
| `max_files` | 20 | 每个级别保留 20 个文件（glog 默认保留更多，容易慢慢吃满磁盘） |
| 统计打印间隔 | 5 秒 | 用于判断"有没有数据""有没有积压"，5 秒不会刷屏也足够及时 |

**关于 `SO_RCVBUF` 的一个真实行为**：Linux 内核会把设置值翻倍（用于缓冲区记账），
所以设 65536 后 `getsockopt` 可能返回 131072。程序启动时会把请求值和实际值都打进日志，
避免"以为调大了其实没生效"。

## 5. 日志级别使用约定

| 级别 | 本项目的使用场景 |
|---|---|
| INFO | 启动/退出、生效配置、周期统计、空闲统计、退出汇总、`[原始报文]`、`[数据]` |
| WARNING | 队列满丢包、**队列高水位预警（>=75%）**、真实解析失败、零长包、`setsockopt` 失败 |
| ERROR | socket 创建/绑定失败、`recvfrom` 异常、写日志文件失败 |
| FATAL | 未使用。进程该不该继续由 `main` 返回值决定，不用 FATAL |

**统计日志的三种形态**（都带 `累计…` 与 `队列深度=X/Y 峰值深度=Z`）：

| 标签 | 何时出现 | 用途 |
|---|---|---|
| `[接收统计]` / `[处理统计]` | 每 5 秒（有数据在流动时） | 观察吞吐与积压 |
| `[接收统计·空闲]` / `[处理统计·空闲]` | 每 5 秒（无数据时） | **区分"MCU 没发"和"程序没收"**。从未收到数据时会额外提示检查 MCU / bind_ip / 防火墙 |
| `[…线程退出]` | 线程结束时 | 任何时长的运行都有完整汇总，含丢包率与峰值深度 |

> **设计教训**：最早的版本把统计只写在"成功收到包"的分支里，结果是
> **MCU 一个包都不发时日志完全静默** —— 恰恰是排障最需要信息的时刻。
> 统计必须由"时间"驱动，不能由"事件"驱动。

**降频手段**（高频场景必备，否则日志会撑爆磁盘）：

| 场景 | 手段 | 位置 |
|---|---|---|
| 队列满丢包刷屏 | `LOG_EVERY_N(WARNING, 100)` | `app.cpp` 接收线程 |
| 解析失败刷屏 | `LOG_EVERY_N(WARNING, 20)` | `app.cpp` 处理线程 |
| 零长包刷屏 | `LOG_EVERY_N(WARNING, 100)` | `app.cpp` 接收线程 |
| `recvfrom` 错误刷屏 | `LOG_EVERY_N(ERROR, 20)` | `app.cpp` 接收线程 |
| 正常数据量太大 | 每 5 秒一条统计；如需逐包记录，后续可加"抽样"配置 | 待协议确定后再定 |

**关于 `峰值深度`（新增的关键指标）**：它比"丢了多少"更能说明问题。

| 峰值深度 | 含义 |
|---|---|
| 0 或个位数 | 消费远快于生产，健康 |
| 偶尔接近容量 | 有洪峰但能吸收，可接受 |
| **长期贴着容量上限** | **结构性瓶颈，消费能力不足**，丢包只是时间问题 |

所以程序在深度达到 75% 时就发 WARNING —— **在丢包发生之前预警**，
而不是等丢包了才告诉你。

## 6. 联调检查清单

按顺序做，每步都要看到预期结果再进下一步。详细的学习路径见计划书第 7 节。

### 6.1 构建与启动
- [ ] `./scripts/build.sh` 编译无报错（警告可以暂时忽略，但要记录）
- [ ] `./scripts/run.sh` 启动，终端能看到"UDP 监听已就绪: 0.0.0.0:9000"
- [ ] `ls logs/` 能看到 `udp_logger.INFO` 软链接和带时间戳的实际文件
      （**注意软链接名字必须是 `udp_logger.INFO`，不能是 `udp_logger.INFO.INFO`**）
- [ ] `grep "生效配置" "$(ls -t logs/udp_logger.INFO.* | head -1)"` 能核对到全部配置
- [ ] `date` 确认虚拟机系统时间正确（时间错则日志失去对齐价值）

### 6.2 基本收发
- [ ] `ss -lunp | grep 9000` 显示监听中
- [ ] `./build/udp_sender -n 10` 后，日志出现 10 条 `[原始报文]`
- [ ] `logs/raw/udp_raw.log` 里有 10 行，hex 与发送内容一致
- [ ] `echo -n "hello" | nc -u 127.0.0.1 9000` 能被记录，len=5

### 6.3 边界情况
- [ ] `-s 0`（零长包）：日志出现"收到长度为 0 的数据报"，不崩溃
- [ ] `-s 1200`（大包）：完整记录，hex 无截断（`max_payload_hex_bytes` 只影响日志显示）
- [ ] `-x "DE AD BE EF"`：当前被记为 `[原始报文]`；协议实现后应记为 `[解析失败] reason=BAD_MAGIC`
- [ ] 两个实例同时运行：第二个应 `bind` 失败并给出清晰提示

### 6.4 过载与丢包
> **前提：测试时长必须明显大于统计间隔（5 秒）。** 5 秒的测试最多只能跨过一个
> 统计周期，甚至一条统计都看不到；而且短测试只测到"最恶劣的初始饱和阶段"，
> 丢包率会被显著放大（同样 capacity=16、2 万包/秒，5 秒测出 29%，25 秒测出 17%）。
> 评价稳态性能请跑 **30 秒以上**。

- [ ] `./build/udp_sender -n 100000 -r 20000` 猛发，观察 `[接收统计]` 里的累计丢弃
- [ ] 把 `queue.capacity` 改成 16 重启，重新猛发，确认丢包计数明显上涨且**程序不崩**
- [ ] 丢包时日志里能看到 WARNING（降频后约每 100 次一条）
- [ ] 观察 `峰值深度` 字段：它比"丢了多少"更能说明"离丢包还有多远"
- [ ] 深度达到 75% 时应出现"消费速度可能跟不上"的预警 WARNING（还没丢包就先预警）
- [ ] 逐级降速找安全红线：固定 `-n 50000`，依次试 20000 / 15000 / 12000 / 10000 / 8000，
      找出**零丢包的最高速率**，留 20% 余量作为现场部署依据

### 6.5 优雅退出
- [ ] `Ctrl+C`：1 秒内退出，退出日志齐全（接收汇总 / 处理汇总 / 所有线程已退出）
- [ ] 接收线程的退出汇总里能看到 `丢包率=` 和 `峰值深度=`
- [ ] `kill -TERM <pid>`：同上
- [ ] 退出前故意发一批包，确认队列里的数据被处理完（处理数 = 接收数）
- [ ] 用 `kill -9` 对比：日志可能缺最后几行 —— 说明为什么必须优雅退出

### 6.5b 空闲可见性（新增行为）
- [ ] **不启动 `udp_sender`**，静等 10 秒：日志里应出现 `[接收统计·空闲]`，
      并且第一条会带上"自启动以来未收到任何数据…请检查 MCU 是否在发送…"的提示
- [ ] 处理线程也应有 `[处理统计·空闲]`，且带上"距上一个包 Xms"
- [ ] 开始发包后，空闲提示停止，出现正常的 `[接收统计]`
- [ ] 发完包停手，`距上一个包` 的数值应持续增大（说明数据真的停了）

### 6.6 资源与长稳
- [ ] `htop` 里能看到两个线程名 `udp-recv` / `udp-parse`
- [ ] 空闲时 CPU 接近 0%（说明消费者在睡眠而不是空转；
      处理线程用 200ms 超时轮询，唤醒开销可忽略）
- [ ] 连续运行 2 小时，`ps` 观察 RSS 无持续增长（无内存泄漏）
- [ ] 日志文件超过 `max_size_mb` 后会轮转；启动时旧文件被清理到 `max_files` 个

### 6.7 故障注入
- [ ] 运行中 `rm -rf logs`：程序应自愈（自动重建目录），并在日志里报错但继续运行
- [ ] 把日志目录 `chmod 500`：应看到写失败告警，程序不崩
- [ ] 配置文件改成 Tab 缩进：启动应报清晰的 YAML 错误并退出
- [ ] `bind_port` 改成 `"abc"`：应报类型错误并退出
- [ ] 把 `bind_ip` 改成 `127.0.0.1` 后从另一台机器发包：收不到（验证"必须绑对外网卡"）

## 7. 排障思路（按顺序做，能快速定位问题在哪一层）

```
收不到数据
   │
   ├─ 1. tcpdump -i any -n udp port 9000
   │      ├─ 抓到包 → 问题在程序侧 → 看 bind_ip 是否绑错网卡、端口是否一致
   │      └─ 抓不到 → 问题在网络/MCU 侧 → ping、ip addr、防火墙、网段
   │
   ├─ 2. ss -lunp | grep 9000     确认端口真的在监听
   ├─ 3. 日志里"UDP 监听已就绪"那行的 IP:端口是否与预期一致
   └─ 4. netstat -su | grep -i error   看内核层 UDP 错误计数
```

```
丢包
   │
   ├─ 日志里"累计丢弃"在涨 → 队列满，处理线程跟不上
   │     → 加大 queue.capacity，或减少日志量（关掉逐包 INFO）
   ├─ netstat -su 里 "receive buffer errors" 在涨 → 内核缓冲区满
   │     → 加大 recv_buffer_bytes
   └─ tcpdump 抓到的包数 < MCU 声称的发送数 → 链路/交换机侧丢包
```

```
程序退不掉
   │
   ├─ 检查信号处理函数里是否出现了 LOG()/printf（必须只写 atomic）
   ├─ 检查是否漏了 queue.Close()（处理线程会永远睡在 wait 上）
   └─ 检查 recv_timeout_ms 是否被设成很大
```
