### 2025-XX-XX 【已解决·首次构建】error: use of deleted function ... LockFreeQueue<T>::operator=
- **现象**：
  ```
  /home/wh/桌面/udp_logger/src/main.cpp:102:51: error: use of deleted function
  'udplog::LockFreeQueue<T>& udplog::LockFreeQueue<T>::operator=(const udplog::LockFreeQueue<T>&)
  [with T = udplog::RawPacket]'
  ```
  出错代码是 `app.queue = udplog::LockFreeQueue<udplog::RawPacket>(capacity);`
- **原因**：队列内含 `std::mutex` 和 `std::condition_variable`，两者本身不可拷贝也不可移动。
  更要紧的是 C++ 的一条规则：**只要用户显式声明了拷贝赋值（哪怕是 `= delete`），
  移动赋值就不会被隐式生成**。于是 `= LockFreeQueue<T>(n)` 这个右值只能去匹配
  被删除的拷贝赋值，编译失败。
- **解决**：不要"先默认构造再赋值"，而是让容量在构造时一次定好：
  ```cpp
  // include/app.h
  explicit App(const AppConfig& cfg)
      : config(cfg), queue(static_cast<size_t>(cfg.queue.capacity)) {}
  // src/main.cpp
  udplog::App app(config);   // 替代 app.queue = ...; 的写法
  ```
  同时把队列的拷贝构造、拷贝赋值、移动构造、移动赋值**四个全部显式 delete**，
  避免以后有人再踩同一个坑。
- **花费时间**：10 分钟

### 经验：为什么队列不该被赋值
队列是"有身份的运行时对象"——接收线程和处理线程都持有它的引用。
一旦被复制或搬移，线程就会操作一个"孤儿队列"，表现为：
- 收包线程往 A 队列写，处理线程从 B 队列读 → 数据全部进不来；
- 或者两个线程操作已析构的内存 → 崩溃。
所以正确做法是**容量在构造时一次决定**，之后永不拷贝、永不移动。

### 2025-XX-XX 【已解决】日志软链接名字变成 udp_logger.INFO.INFO，tail 报"没有那个文件"
- **现象**：
  ```
  ls -l logs/
  lrwxrwxrwx ... udp_logger.INFO.INFO -> udp_logger.INFO.20261013-124042.41898
  $ tail -f logs/udp_logger.INFO
  tail: 无法打开'logs/udp_logger.INFO' 读取数据: 没有那个文件或目录
  ```
  误以为是"必须先收到 MCU 数据才会有日志"。
- **原因**：glog 的 `google::SetLogSymlink(severity, base)` 参数**只是前缀**，
  glog 会在后面自动追加 `.INFO` / `.WARNING` 等。传 `"udp_logger.INFO"` 就多出一层。
  同理 `SetLogDestination` 的参数也是"目录 + 文件名前缀"。
- **解决**：软链接改用 `FLAGS_log_link`（它是"链接名基底"，glog 会自动追加 `$LEVEL`）：
  ```cpp
  FLAGS_log_link = cfg.file_prefix;   // 得到 udp_logger.INFO
  ```
  并在启动日志里自检软链接是否存在、打印出可复制的 `tail -f` 命令。
- **顺带纠正一个误解**：日志**不是**"收到数据才写"。启动横幅、生效配置、
  "UDP 监听已就绪"在程序起来的那一刻就已落盘（`FLAGS_logbufsecs = 0`，每条立即 flush）。
  文件大小 4KB 左右也印证了这一点。
- **花费时间**：5 分钟

### 经验：临时怎么看日志（不用改代码）
```bash
# 看目录里最新的 INFO 文件
tail -f "$(ls -t logs/udp_logger.INFO.* | head -1)"
```

### 2025-XX-XX 【已解决】统计日志只有两条，误以为"每 5 秒打印统计"的代码坏了
- **现象**：压测 `./build/udp_sender -n 100000 -r 20000` 之后，
  `grep "接收统计"` 只能查到 2 条，怀疑统计代码有问题。
- **排查过程**：
  1. `wc -l` 看到文件有 71290 行，**说明日志一直在写**，不是日志系统坏了；
  2. `grep -n "统计"` 发现这 4 条统计的行号是 19、21、71266、71269 ——
     **中间 71000 多行全是压测产生的逐包日志**；
  3. 算一下时间：`-n 100000 -r 20000` = **只发 5 秒**，而统计间隔也是 5 秒，
     所以最多只能跨过 1~2 个统计周期。
- **结论**：**不是 bug，是测试时长太短**。统计恰好卡在压测起点（累计收到=1）
  和终点（累计收到=99818）上，运气已经算好了——再多偏 100ms 就一条都看不到。
- **教训（重要）**：
  1. **测试时长必须显著大于统计间隔**。想评价稳态性能，至少跑 30 秒以上；
     5 秒的测试只会测到"最恶劣的初始饱和阶段"，丢包率会被显著放大
     （同样是 capacity=16、2 万包/秒，5 秒测出 29%，25 秒测出 17%）。
  2. **看统计要用 `grep "统计"`，不要只 grep `接收统计`**，否则会漏掉 `处理统计`。
  3. 每次测试前先想一想"这次测试会经历几个统计周期"，否则很容易误判。
- **花费时间**：20 分钟（含来回确认）

### 这次测试暴露的真实问题（已修）
统计代码**只写在"成功收到包"的分支里**，导致：
- MCU 一个包都不发时，日志**完全没有记录**（恰恰是排障最需要信息的时刻）；
- 运行时长 < 5 秒时，可能一条统计都没有。

修复内容：
1. 空闲也汇报：`[接收统计·空闲]` / `[处理统计·空闲]`，并带上"距上一个包 Xms"；
   从未收到过数据时还会额外提示检查 MCU / bind_ip / 防火墙。
2. 退出时打印最终汇总：任何时长的运行都会留下完整记录（含丢包率、峰值队列深度）。
3. 新增**峰值队列深度**和**高水位告警**（深度 >= 75% 就 WARNING），
   这样"快追不上了"能被提前发现，而不用等到开始丢包。
4. `WaitPop()` 增加了超时版本（返回 `kGotItem` / `kTimeout` / `kClosed` 三态），
   让处理线程也能周期汇报。注意超时值取自固定常量，**不能**用"距下次汇报的剩余时间"
   —— 否则某个包处理超过 5 秒后，剩余时间变成 1ms，会造成每个包汇报一次、
   日志被瞬间刷爆。

### 这次测试的量化收获
| 指标 | 数值 |
|---|---|
| 发送 | 100000 个包（5 秒 @ 2 万包/秒） |
| 应用从内核读出 | 99818（**内核侧仅丢 182 个，0.18%**） |
| 应用层队列丢弃 | 28859（28.9%） |
| 成功处理 | 70959 ≈ **14200 包/秒** |

结论：**瓶颈完全在应用层的日志写入，不在网络和 socket**。
这套日志策略（逐包 glog + 逐包原始文件开关）的吞吐上限约 **1.4 万包/秒**。

### 2025-XX-XX 【已解决】队列丢包 34653 个，却一条"高水位预警"都没有
- **现象**：capacity=16，压测 60 万包，退出汇总显示
  `累计收到=600000 累计丢弃=34653`（丢包率 5.46%），
  但 WARNING 文件里**只有"队列已满"，没有一条"队列深度已达"**。
  采样依据：接收线程 `峰值深度=8/16`（50%），处理线程 `峰值深度=15/16`（93%）。
- **原因（我的设计缺陷）**：预警条件写在 `report()` 里，判断的是**汇报那一刻的
  瞬时深度**。而队列饱和时深度会稳定在"丢一点、收一点"的**平衡点上**
  （实测约 8/16 = 50%），峰值却会冲到 15/16。
  每 5 秒才采样一次，几乎不可能恰好抓到峰值 → **必然漏报**。
  `peak_depth` 明明是接收线程自己数出来的 8，而它看到 15 的那个瞬间没有被检查。
- **更深一层的教训**：**"用采样值代表整段时间"是错误的做法**。
  正确思路是记录"整段是否曾经越线"。而且最可靠的越线证据根本不需要采样 ——
  **`TryPush` 返回 false 就说明队列必然满过（100%）**，零开销、零漏报。
- **解决**：
  1. 增加 `high_water_seen` 粘滞标志：一旦越线就保留到下次汇报，不漏报；
  2. `TryPush` 失败时直接置位（并记录 `peak_depth = capacity`），
     这是"已经过载"的铁证；
  3. 成功入队时**每 64 个包**才调一次 `queue.Size()` 采样深度 ——
     避免在收包热路径上抢锁（收包延迟直接影响内核缓冲区是否溢出丢包）；
  4. 告警里带上"本周期丢弃 N 个"，让严重程度一目了然。
- **花费时间**：30 分钟（含来回验证）

### 经验：怎么证明"日志有没有丢"
`累计收到 = 累计处理 + 累计丢弃` 且 `队列残留 = 0`。
实测：`600000 = 565347 + 34653` ✅，569740 行日志与处理数吻合 ✅。
这两个等式成立，就说明"数据完整、没有静默丢失"。

### 经验：`累计收到` 与发送总数对比，能区分"内核丢"还是"应用丢"
发送 600000，`累计收到=600000` → **内核侧一个没丢**（接收线程够快），
丢包全部发生在应用层队列 → 瓶颈在日志写入，不在网络。

### 2025-XX-XX 【待解决】glog 在 10MB 就轮转，但配的是 100MB
- **现象**：`单文件上限: 100MB` 已在启动日志里确认，但
  `udp_logger.INFO.20261015-162911.14400` 在 **10,485,769 字节（正好 10 MiB + 9）**
  处被切成第二个文件，同一 pid、内容时间连续（确认是轮转而非重启）。
- **已排除**：
  - glog 本身没问题 —— 最小复现程序（120000 行 × 240 字节 ≈ 28.8MB，
    `FLAGS_max_log_size = 100`）**只产生一个文件，完全不轮转** ✅
  - 不是跨天（两个文件名日期都是 20261015）
  - 不是程序重启（两个文件 pid 都是 14400）
  - 不是 `max_files` / `PruneOldLogs`（它们只删除，不创建）
- **待查方向**：对比"最小程序"与"本工程 logger.cpp"的设置差异。
  下一个测试按 `logger.cpp` 的**相同顺序**设置参数
  （`FLAGS_log_dir` → `SetLogDestination` → `FLAGS_max_log_size`），
  并在设置前后打印 flag 值、按严重级别分别打印文件大小，用来定位差异。
- **影响**：文件比预期多出 10 倍 → `max_files: 20` 的名额被快速耗尽，
  有用的历史日志会被提前清掉。**在定位之前，建议把 `max_files` 临时调大到 100。**
